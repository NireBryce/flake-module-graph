# Proposing an issue

## Applies to

A genuine problem in **this repository** -- a bug, a missing test for a
failure that can happen, a doc that is wrong -- noticed while doing
something else, and too big or too far off-task to fix now. Not for
upstream projects: never file anywhere but this repository unless the user
says so explicitly, in those words.

## Before proposing

- Search first: `gh issue list --search "<keywords>" --state all`.
- Reproduce it, or say plainly that you didn't.
- Check the repo isn't already handling it (an open PR, a TODO with an
  issue number).

## Propose, then file only on a yes

Show the user a title and a body, and ask. The body:

```
🤖 Generated by an LLM agent

## What happens
<observed, with the command and its output>

## Expected
<what should happen, and why>

## Where
<file:line, or the doc section>

🤖 Generated by an LLM agent
```

Then `gh issue create --title "<title>" --body-file <file>`.

**Grep the draft for `owner/repo#123` shapes before filing**: GitHub
autolinks them, which pings that other project. Write such references as
plain text (`owner/repo issue 123`) unless the user wants the link.

Public text stays mechanical: what is wrong and how to see it. If the
problem is a security weakness, describe the fix needed, not what an
attacker could reach.
